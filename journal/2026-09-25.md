## 1. 三个布局工具

| 工具 | 作用 |
| --- | --- |
| `sizeof` | 查看对象或类型占用的总字节数，包括填充字节。 |
| `_Alignof` | 查看类型的对齐要求。 |
| `offsetof` | 查看结构体成员相对结构体起点的字节偏移。 |

`offsetof` 需要包含 `<stddef.h>`。以上结果的类型都是 `size_t`，打印时使用 `%zu`。

例如，4 字节对齐表示对象的起始地址必须是 4 的整数倍。对齐要求与类型大小是两个概念，不能一律将二者视为相等。

本次实验环境为 x86-64、GCC；当前机器报告的缓存行大小为 64 字节。以下布局以该环境的实测结果为准，不是所有平台都保证相同。

## 2. 结构体对齐与填充

普通结构体在当前环境下可以按以下顺序分析：

1. 按成员声明顺序安排位置。
2. 放置每个成员前，将偏移推进到满足该成员对齐要求的位置，必要时加入中间填充。
3. 成员放置完毕后，将总大小补到结构体对齐要求的整数倍，必要时加入尾部填充。

普通情况下，结构体的对齐要求由对齐要求最大的成员决定；显式对齐或打包设置可能改变布局。尾部填充保证结构体数组的后续元素也能满足对齐要求。

### A：`char / int / char`

```c
struct A {
    char a;
    int b;
    char c;
};
```

| 内容 | 字节偏移 | 占用字节数 |
| --- | --- | ---: |
| `a` | 0 | 1 |
| 中间填充 | 1～3 | 3 |
| `b` | 4～7 | 4 |
| `c` | 8 | 1 |
| 尾部填充 | 9～11 | 3 |

成员大小之和为 6 字节，但包含填充后，`sizeof(struct A) == 12`，对齐要求为 4 字节。

### B：`int / char / char`

```c
struct B {
    int b;
    char a;
    char c;
};
```

| 内容 | 字节偏移 | 占用字节数 |
| --- | --- | ---: |
| `b` | 0～3 | 4 |
| `a` | 4 | 1 |
| `c` | 5 | 1 |
| 尾部填充 | 6～7 | 2 |

`sizeof(struct B) == 8`，对齐要求为 4 字节。与 A 相比，仅调整成员顺序，就减少了 4 字节。

### C：`char / double / int`

```c
struct C {
    char a;
    double b;
    int c;
};
```

| 内容 | 字节偏移 | 占用字节数 |
| --- | --- | ---: |
| `a` | 0 | 1 |
| 中间填充 | 1～7 | 7 |
| `b` | 8～15 | 8 |
| `c` | 16～19 | 4 |
| 尾部填充 | 20～23 | 4 |

`sizeof(struct C) == 24`，对齐要求为 8 字节。

### 实测结果

```text
char:   size=1 align=1
int:    size=4 align=4
double: size=8 align=8
A: size=12 align=4 offsets(a,b,c)=0,4,8
B: size=8 align=4 offsets(b,a,c)=0,4,5
C: size=24 align=8 offsets(a,b,c)=0,8,16
```

## 3. 缓存行与伪共享

缓存一致性机制以缓存行为单位协调不同核心的数据访问。当前机器一条缓存行占 64 字节，这不是 C 语言规定的固定大小。

假设两个线程运行在不同核心上，各自频繁修改一个计数器。如果两个计数器位于同一条缓存行，写入时就可能反复争用该缓存行的写权限，使其他核心的相关缓存副本失效，产生额外的一致性开销。

```text
同一条缓存行（64 字节）
[计数器 A：8 字节][计数器 B：8 字节][其余部分]
       线程 0 写          线程 1 写
```

这就是伪共享：逻辑上使用不同变量，硬件上却共享同一条缓存行。写／写、写／读都可能产生这种干扰。

**修正原先的理解：** 伪共享不是让另一个线程无法更新计数器，而是可能拖慢更新。它是性能问题；如果多个线程未同步地访问同一个普通变量且至少一个写入，还需要另外处理数据竞争。

## 4. 相邻计数器的布局

```c
#include <stdint.h>

struct SharedCounters {
    uint64_t a;
    uint64_t b;
};

_Alignas(64) struct SharedCounters shared = {0};
```

实测输出：

```text
SharedCounters: size=16 type_align=8 (object aligned to 64)
shared.a: address=0x7fff69660f40, offset_in_line=0
shared.b: address=0x7fff69660f48, offset_in_line=8
```

- `a` 占 8 字节，位于结构体偏移 0～7。
- `b` 占 8 字节，位于结构体偏移 8～15。
- 整个结构体共占 16 字节，因此 `b` 从偏移 8 开始，与总大小 16 并不矛盾。
- 类型本身的对齐要求为 8 字节；这里单独要求对象 `shared` 按 64 字节对齐，内部成员间距仍然不变。

`offset_in_line` 表示地址相对所在缓存行起点的偏移。由于这个对象从缓存行边界开始，成员在缓存行内的偏移恰好等于其在结构体内的偏移。两个成员仍位于同一条缓存行，不同核心频繁更新它们时可能出现伪共享。

## 5. 隔离计数器的结构体

```c
#include <stdint.h>

struct CounterSlot {
    _Alignas(64) uint64_t value;
};

struct CounterSlot counters[2] = {0};
```

### 代码含义

- `<stdint.h>` 提供 `uint64_t`，它是恰好 64 位的无符号整数类型，在当前环境中占 8 字节。
- `_Alignas(64)` 指定成员 `value` 的 64 字节对齐要求，也使包含它的结构体需要满足该对齐要求。
- `value` 本身仍占 8 字节。当前环境中，编译器加入 56 字节尾部填充，使整个结构体占 64 字节。
- `counters[2]` 创建两个结构体元素，总大小为 128 字节。
- `= {0}` 将两个元素的 `value` 都初始化为 0；不应据此推断填充字节的具体内容。

```text
缓存行 0：[counters[0].value：8 字节][尾部填充：56 字节]
缓存行 1：[counters[1].value：8 字节][尾部填充：56 字节]
```

### 实测结果

实验源码中的数组名为 `isolated`，布局与上面的 `counters` 相同：

```text
CounterSlot: size=64 align=64
isolated[0].value: address=0x7fff69660f80, offset_in_line=0
isolated[1].value: address=0x7fff69660fc0, offset_in_line=0
```

两个地址相差 `0x40`，即 64 字节。两者都位于各自缓存行的起点，而不是位于同一条缓存行。

这个设计可以避免两个计数器之间因共用一条缓存行而产生的伪共享，但不保证程序没有其他争用，也不提供线程同步。若多个线程同时修改同一个 `value`，仍需使用适当的同步机制。

## 7. 今日易错点与后续练习

- **大小与起始偏移不同：** `b` 从偏移 8 开始，占 8 字节，所以结构体到偏移 15 结束，总大小为 16 字节。
- **64 位与 64 字节不同：** `uint64_t` 占 8 字节；`_Alignas(64)` 要求 64 字节对齐。
- **对齐整个对象不等于隔离内部成员：** `shared` 对齐到缓存行起点后，`a`、`b` 仍然相邻。
- **相同的行内偏移不代表同一条缓存行：** 两个隔离计数器的 `offset_in_line` 都为 0，但地址相差 64 字节。
- **布局验证不等于性能验证：** 后续可比较相邻计数器与隔离计数器的多线程更新耗时，保持更新方式一致，并重复测量。

设计时需要权衡空间与访问方式：紧凑布局节省空间；隔离不同核心频繁修改的数据可以减少相互干扰，但会增加内存和缓存占用。
